# 07. 의사결정 비교 분석 (D-01 · D-03 · D-04/05 · D-07 · D-08 · D-11)

> 방법: 결정마다 **선택지 → 평가 기준(가중치) → 1~5점 채점 → 가중 합계(100점 환산) → 권장안과 전환 조건**.
> 법적 필수 요건을 충족하지 못하는 선택지는 점수와 무관하게 **탈락(게이트)** 처리합니다.
> 점수는 현재까지의 분석(부록 A1~A3)과 팀 구성(1차 커밋 기준: React/TypeScript 프론트 3명, Django 백엔드 3명)에 근거한 판단입니다. 라이브러리 지원 여부처럼 검증이 필요한 부분은 **PoC 항목**으로 따로 적었습니다.

### 권장안과 전환 조건
- **권장: R(React Native).** 팀 역량과 일정 측면의 이점이 크고, 접근성·네이티브 기능 차이는 네이티브 모듈로 메울 수 있습니다.
- **민감도:** 팀 역량 가중치만 5로 낮추면 R 77.8 : K 76.7로 거의 동률이 되고, 여기에 네이티브 기능(25)·유지보수(15) 가중치를 올리면 K가 앞섭니다(79.0 : 77.0). 즉 **Android 네이티브 경험자를 투입할 수 있거나 알람·접근성 안정성을 최우선으로 두면 K**가 맞습니다.
- **1주 PoC 게이트** — R로 아래 5개를 구현해 실제 기기(삼성 One UI + 픽셀)와 TalkBack에서 확인합니다. **하나라도 실패하면 K로 전환**합니다.
  1. 스크롤 강조 목록: TalkBack 탐색, [이전][다음] 버튼, 항목 변경 시 낭독이 자연스러운지
  2. 정확한 알람: `SCHEDULE_EXACT_ALARM` 허용 흐름, Doze 상태에서 정시 울림, 재부팅 후 재등록, 전체화면 알림(허용 시)과 대체 알림
  3. 음성: `SpeechRecognizer` 온디바이스 인식(가능 기기), 한국어 숫자·날짜 인식, TalkBack과 앱 TTS가 겹치지 않는지
  4. 카메라: ML Kit 바코드 실시간 인식 + 진동 + 자동 촬영, 한글 영양성분표 OCR
  5. 인증: Firebase Phone Auth 자동 인증(SMS 권한 없이)

### 권장안
- **권장: A.** 2차 의뢰서(§7 "Android 기본 음성 인식 + 후처리, 음성 명령은 키워드 매칭")와도 일치합니다.
- 유저테스트에서 필드별 인식 성공률이 90%에 못 미치면 D(서버 LLM 보조, 명시적 동의 후)를 추가 검토합니다.

### 공개 레포에서 실제로 문제가 되는 것 (조사 결과)
| 항목 | 현황 | 인증 키 분리로 해결되나 |
|---|---|---|
| 인증 키·시크릿 | 전체 커밋 기록에서 AWS·Google API 키, 서비스 계정 키, OAuth 시크릿은 **발견되지 않음**. 개발용 Django `SECRET_KEY`만 `settings.py`에 하드코딩 | **예** — 환경변수화 + 운영 키 신규 발급 |
| 내부 문서 | `prototype` 브랜치 `refs/`에 **회의록(보수·비용 논의 포함), 개발 의뢰서, 운동 가이드 원고(docx)**가 공개돼 있음 | 아니요 |
| 콘텐츠 원본·자산 | 같은 `refs/`에 **픽토그램 원본(.ai)**, `dev`에 픽토그램 112장, 운동 가이드 대본 전문(fixtures) | 아니요 |
| 라이선스 | 레포 루트는 **Apache-2.0**, 프론트 package.json은 MIT → 공개 상태에서는 누구나 상업적으로 복제·재사용 가능. 디자인팀·가이드팀 저작물이 이 조건으로 공개되는 데 저작자 동의가 있었는지 불명확 | 아니요 |
| 보안 결함 | 무인증 STT 등 결함이 코드에서 보임 | 아니요 — 다만 **비공개로 돌려도 고쳐야 하는 문제**. 서버를 외부에 띄우기 전에 수정하면 됨 |

→ 즉 **인증 키는 분리만 하면 되는 작은 문제**이고, 공개 유지의 실제 쟁점은 **내부 문서·콘텐츠 저작물·라이선스**입니다. 이 셋을 정리하면 공개 레포도 충분히 안전하게 운영할 수 있습니다.

### 선택지 비교
**게이트:** 보안 취약점 세부 근거와 시크릿 보관 위치를 공개 장소에 두는 안은 탈락.

| 기준 | 가중치 | ① 공개 유지 + 시크릿·내부 문서·콘텐츠 원본 분리 | ② 레포 비공개 전환 | ③ 공개 레포에서 앱 코드만, 백엔드는 비공개 레포 분리 |
|---|---|---|---|---|
| 보안(시크릿·내부정보 노출) | 30 | 4(분리 규칙과 자동 검사가 지켜질 때) | 5 | 4 |
| 저작권·라이선스 정리 | 20 | 3(자산 분리·라이선스 명시 작업 필요) | 5 | 3 |
| 공개·포트폴리오·기여 가치(접근성 서비스의 공개 코드) | 20 | 5 | 1 | 4 |
| 운영 부담 | 15 | 4 | 5 | 2(레포 2개, 계약 동기화) |
| 비개발 팀 접근성(Drive 공유본 병행) | 15 | 4 | 4 | 4 |
| **합계(100점)** | | **80** | **81** | **70** |

- ①과 ②는 사실상 동점(80 : 81)이라 **팀이 공개로 얻는 가치(포트폴리오·SSAFY 결과물·오픈 접근성 서비스)를 원한다면 ①이 맞습니다.** 사용자 제안(공개 + 인증 키 별도 관리)을 채택하되, 아래 조건을 **함께** 적용합니다.

### ①을 채택할 때 필수 조치
1. **시크릿:** `SECRET_KEY`·DB 비밀번호 등 모든 설정을 환경변수로(`.env`는 git 제외 유지), 운영 키는 새로 발급해 GitHub Secrets / AWS Secrets Manager에만 보관. GitHub **secret scanning + push protection** 켜기, CI에 시크릿 검사(gitleaks 등) 추가.
2. **내부 문서 제거:** `prototype` 브랜치 삭제(회의록·의뢰서·원고·.ai 원본). 브랜치를 지워도 커밋은 해시로 한동안 접근 가능하고 포크에 남을 수 있으므로, 민감도가 높다고 판단되면 GitHub 지원팀에 캐시 삭제를 요청합니다. 앞으로 내부 문서는 Drive `테크팀/`에만 둡니다.
3. **콘텐츠 자산 분리:** 픽토그램·운동 음성·가이드 대본은 레포에서 빼고 S3(비공개 원본 + CloudFront 공개 배포본)로 이동. 레포에는 샘플 몇 개와 불러오는 스크립트만. 공개를 유지할 자산은 저작자(디자인팀·가이드팀) 동의를 받고 코드와 **별도 라이선스**(예: CC BY-NC)로 명시.
4. **라이선스 정리:** 코드 라이선스를 하나로(Apache-2.0 유지 여부 결정, package.json MIT 표기 정리). 외주 계약서의 저작권 양도 조항과 충돌하지 않는지 확인.
5. **보안 결함은 서버 공개 전에 수정**(01 문서 P0).
6. **문서 보관:** `docs/design/` 01~07은 공개 레포, 세부 근거 부록(A1~A3)과 계정·비밀 정보는 Drive `테크팀/` 비공개 폴더(또는 비공개 저장소).
